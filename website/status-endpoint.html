DEVELOPER USAGE GUIDE

A small API.
A deliberate handoff.

The examples below explain the implemented contract. They require approved task access; copying them does not enroll you or create a task.

  1. Sign up or sign in to NektronAI.

    Status Endpoint is part of the NektronAI ecosystem and requires a NektronAI account, using the same account system as Database Connector. Create your NektronAI account, or sign in with your existing account. You do not need a separate Status Endpoint account.

    Account registration is the first step; it does not automatically enable Status Endpoint or grant access to any task. Self-service Status authorization is still in development. Contact Nektron to discuss your integration. For an approved setup, an administrator must register the tenant, account membership, task, producers, work assignments and result authority, then deliver separate expiring grants through an approved secret channel. The deployed evidence API currently has no public task-creation or token-issuance endpoint.

    Use a dedicated task-status:publish grant for a producer and task-status:read for a consumer. Overall results also require task-status:result and the designated authority identity. Internal details and evidence require the separate task-status:read-internal permission with read access.

  2. Connect from your application.

    Use native HTTPS at https://status.nektron.ai, with the prefix /api/task-status/v1. Send Authorization: Bearer <status-token> on each request and JSON for publishing. Your shared NektronAI account establishes your identity. A website session, Database Connector credential or Mail sign-in token alone does not authorize Status API requests; Status Endpoint uses its own approved scopes and task grants. Browser cookies and browser-origin requests are rejected; integrate through an authorized native client or backend.

    Keep credentials in your application's approved secret store. Never place them in this page, a URL, chat, source code or an event.

  3. Save an event, then publish it.

    Create a new UUID event ID and save the JSON before sending it. Use your assigned work-item ID, current generation, next revision and actual UTC timestamp. This synthetic example reports implementation only; it makes no deployment or verification claim.

    Example saved-event.json
    {
  "event_id": "10000000-0000-4000-8000-000000000001",
  "kind": "work_item.status",
  "work_item_id": "reporting-query",
  "generation": 1,
  "revision": 1,
  "status": "implemented",
  "occurred_at": "2026-11-04T12:00:00Z",
  "customer_summary": "Query prepared. Release and checks are pending.",
  "evidence": [{"reference": "urn:nektron:example:local-check-1"}]
}

    Replace every synthetic ID, assignment, timestamp and evidence reference with approved real values. A stored reference is not fetched or independently verified by the service.

    Publish and read with the Python CLI

    For approved developers with the supplied status_endpoint package installed (Python 3.12+). Have your local secret manager supply NEKTRON_STATUS_TOKEN. The CLI does not take a token argument. The UUID below is a placeholder task; use the task ID your administrator provides.

    python -m status_endpoint.cli --origin https://status.nektron.ai publish aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa saved-event.json

# Switch to the separate approved reader credential before reading.
python -m status_endpoint.cli --origin https://status.nektron.ai snapshot aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa

python -m status_endpoint.cli --origin https://status.nektron.ai events aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa --limit 50

# On later reads, pass your saved cursor with --after.
python -m status_endpoint.cli --origin https://status.nektron.ai events aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa --after SAVED_CURSOR --limit 50

    The CLI prints untrusted JSON for inspection. Never pipe event content into a shell or treat it as instructions.

  4. Read a snapshot, then follow the history.

    On connection or reconnection, read the snapshot and reconcile the current overall result with your app's saved generation and result revision. Persist the snapshot's exact head cursor with that decision. Read later events using after and save the returned cursor. Use shared per-task polling and idle/error backoff in your consumer; the endpoint does not poll or push updates for you.

    Work revisions begin at 1 per generation and increase by 1. Overall result revisions continue across generations. Verified work is terminal within a generation; only the result authority can explicitly reopen a task into the next generation while preserving history.

Task API reference · prefix /api/task-status/v1
Method & routePurposeAccess
POST /tasks/{task_id}/eventsPublish a saved eventPublish + assigned producer; authority for overall events
GET /tasks/{task_id}/snapshotCurrent overall result, counts and head cursorRead
GET /tasks/{task_id}/events?after=...&limit=50Ordered, resumable historyRead
GET /tasks/{task_id}/work-items/{work_item_id}One work item's revision and stateRead, or its assigned publisher

Retries are part of the contract.

201: a new event was accepted. 200 on an exact retry: the original receipt is returned. After a timeout or 503, resend the saved event with the same ID and field values. 409: reconcile conflicting content or a stale revision; do not invent an ID or increase a revision to force the event through. 429: honor Retry-After with bounded backoff. 401/403: check access with your administrator. If a history read returns 410, fetch a fresh snapshot and reconcile.

Track, create and request dispatch

The local tools can read snapshots, history and work items, create task tracking, request a durable queue entry for a registered agent, and inspect dispatch state. These additions are behind disabled feature gates. A task ID is an identifier, not access; creating a task does not launch an agent.

A worker has its own authorization

The separate worker path binds authorization to the correct NektronAI account, tenant and registered agent. It uses a separate consent flow and short-lived access, with an operator reviewing the exact task before execution. An operating-system login or Codex login alone does not supply this authorization.

Local tests, further live qualification

The OAuth-to-worker flow passed local testing with a simulated runner, and the installed CLI protocol passed a synthetic-provider check. No real-model worker task has been qualified. The current runner candidate is limited to analysis of supplied text; coding, tool use and unattended work are not enabled.

SHARED EVIDENCE. EXPLICIT RESPONSIBILITY.

Keep the facts visible.
Keep decisions in your app.

Status Endpoint records evidence. It does not run agents, inference, remote commands, email, webhooks or background responders.

Access follows a specific task.

Grants bind an identity to one task within one tenant. Read, publish, internal read and overall-result permissions are distinct. Work assignments and the result authority constrain who can report what.

A report is still a claim.

Authentication identifies the permitted producer; it does not prove its statements. Treat summaries and evidence links as untrusted data, render prose as escaped text and review important conclusions independently. Status content cannot authorize tools or change instructions.

Private details need separate access.

Normal reads omit internal prose and evidence references. The field name customer_summary does not guarantee safe content: producers must exclude secrets and personal data, and consumers must review text before sharing it.

Consumers own the next step.

A project assistant can summarize progress; an application can reconcile its workflow. Email recipients, consent, pause state, human takeover and sending permissions stay with the consuming application. A status update grants none of those permissions.

A FEW GOOD QUESTIONS

Before you integrate.

Tell us about your workflow.
Talk to Nektron →

How is this different from Database Connector?

Database Connector helps ChatGPT investigate your database through read-only queries. Status Endpoint records agent-reported task progress and evidence for authorized consumers. Their access grants are separate.

Does it execute work or send notifications?

No. Your agents do the work and publish events. Consumers read snapshots and history and decide what to do. The service supplies no webhook delivery, scheduler, email sender or background polling job.

Do I need a separate Status Endpoint account?

No. Status Endpoint and Database Connector are part of the same NektronAI ecosystem. Sign up for NektronAI or sign in with your existing NektronAI account. An account is required to use Status Endpoint. Account registration is available now, while self-service Status authorization and task creation remain unavailable on the live service. Approved pilot access still requires separately provisioned task permissions.

Can several agents contribute to one task?

Yes. Each registered producer reports its assigned work items. The designated result authority reports the overall task result. All required work in the current generation must be verified before that authority can verify the overall task with evidence.

Is the history an independent audit of truth?

Events are immutable through the runtime API and have server-assigned receipt ordering. They remain producer claims; the endpoint neither fetches evidence nor proves its accuracy. External audit, retention policy and independent verification need their own operational decisions.
